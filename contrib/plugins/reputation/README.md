# Reputation evidence admission

This native plugin compiles an explicit source and signal catalog before it
accepts independent evidence. The core remains protocol-neutral. The current
observation provider validates evidence without writing Redis state.

The complete [operator example](../../../server/docs/examples/go_plugin_reputation.yml)
is the configuration authority for the admission tests. Its values are
calibration examples, not implicit production defaults. It includes a closed
`reputation/observe/v1` schema, a dedicated exact principal, and a deny-by-default
validation target. Storage must be selected by an effect-executing target before
this example can be used as a learning endpoint.

## Ownership and privacy

An `api_caller` source is selected only by the host-authenticated principal,
with exact case-sensitive comparison. A `host_execution` source is selected
only by the host-created module/component/extension/operation/target identity.
The indexes never fall back to each other. Source-policy IDs are globally unique
and remain immutable while their event history exists.

At startup, the host's `policy_admission` read-only projection supplies enabled
state, principals, exact targets/schemas, effective transport limits, and
diagnostic eligibility. It contains no credentials or Policy code. The
module-bound `host_context.module_name` is generated by the runtime and cannot
be overridden by configuration. Every internal source must also match an actual
callback registration retained by this plugin; an unregistered tuple prevents
activation. No internal learning callback is registered by this admission-only
provider.

All raw subject values are bounded to 512 UTF-8 bytes. IP aliases are unmapped,
networks are masked, ASNs are normalized to positive 32-bit decimal values, DNS
names become lower-case IDNA A-labels, accounts use the explicit deployment
normalization choice, and services must match the configured service catalog.
HMAC tags come only from the required host opaque identifier service. Key bytes
never enter plugin configuration. Network derivation uses explicit prefixes;
ASN derivation requires an exact provider binding and the same admitted IP.
Direct ASN input requires a separately authenticated authoritative external
feed. An unavailable ASN seam makes an ASN-dependent observation unavailable.

The example's raw subject records are visible only to the observation provider.
Its provider-owned admitted collection is visible only to the selected storage
owner. None of their fields is expression-visible or exposed to other
providers. Summaries contain only closed validity/reason/origin/kind values and
bounded configured source classes. Caller causality, source names, and evidence
origin are not declared request fields. Unknown fields, aliases that duplicate
an expanded subject, and invalid role/kind combinations reject the entire event.

## Generic extraction

Optional `target_bindings` compile exact targets and scalar or flat-record
subject extractors. Each binding names one local `output_fact` and one to eight
`subjects` with `attribute`, `role`, and `kind`. A record extractor additionally
names `field` and bounded `correlation_fields`; all correlation values come
from that same record. Extraction is bounded to 24 results. These bindings
prepare assessment inputs without a namespace-specific switch. They do not
create additional Policy authority or observation signals.

## Build and validation

Use the repository's coherent native artifact toolchain with exact Go 1.27.0
and `GOEXPERIMENT=runtimesecret`. Host and plugin artifacts must share one
unchanged source snapshot and be restarted together after contract changes.

Run `GOEXPERIMENT=runtimesecret go test ./contrib/plugins/reputation` from the
repository root, followed by `make guardrails` for the full project gate.
The tests cover strict decoding, source identities and grants, temporal and
measurement bounds, canonical duplicates, exact ASN attribution, protected
records, and a correlated non-mail workflow extraction.
